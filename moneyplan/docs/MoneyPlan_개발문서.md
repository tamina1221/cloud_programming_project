# MoneyPlan

## 목표 기반 월별 자금 배분 서비스 개발 문서

> **핵심 한 문장**
> 수입이 들어오거나 바뀌었을 때, 목표를 지키려면 이번 달 어디에 얼마를 넣어야 하는지 계산해 준다.

---

## 1. 프로젝트 개요

### 1.1 프로젝트명

MoneyPlan – 목표 기반 월별 자금 배분 서비스

### 1.2 프로젝트 목적

MoneyPlan은 사용자가 월 수입을 받았을 때 고정 지출, 최소 생활비, 미래 목표(저축·여행 등)를 고려하여 **이번 달 배분 계획을 자동으로 계산**하는 서비스이다.

기존 가계부가 "쓴 돈을 기록"하는 데 초점을 둔다면, MoneyPlan은 "들어온 돈을 어떻게 나눌지"를 먼저 계산한다. 수입이 늘거나 줄면 같은 계산을 다시 실행하여, 어떤 목표가 영향을 받는지 보여준다.

서비스의 중심은 **배분 엔진** 하나이며, 나머지 기능은 엔진의 입력(수입·목표·지출 설정), 출력(대시보드), 보조(소비 기록과 잔액 확인) 역할을 한다.

### 1.3 대상 사용자

- 아르바이트나 급여로 매월 수입이 있는 대학생
- 생활비를 쓰면서 동시에 저축·여행 같은 목표 자금을 모으는 사용자
- 달마다 수입이 달라 배분 계획을 자주 조정해야 하는 사용자

### 1.4 해결하려는 문제

| 번호 | 문제 | MoneyPlan의 해결 방식 |
| --- | --- | --- |
| 1 | 수입을 각 목적에 얼마씩 나눌지 판단하기 어렵다 | 정해진 순서와 우선순위로 자동 배분 |
| 2 | 목표 달성을 위해 매월 얼마를 모아야 하는지 계산하기 어렵다 | 부족액 ÷ 남은 개월 수로 월 필요 적립액 계산 |
| 3 | 수입이 줄었을 때 무엇을 줄여야 하는지 모른다 | 우선순위가 낮은 목표부터 감액하고, 다음 달 필요 적립액을 다시 계산 |
| 4 | 추가 수입이 생겼을 때 기존 계획을 어떻게 바꿔야 할지 모른다 | 기존 배분 유지 또는 재배분 중 선택 |
| 5 | 배분한 돈이 실제로 얼마 남았는지 알기 어렵다 | 목적별 소비를 기록하고 잔액·초과 여부 표시 |

### 1.5 수업 내용과의 연결

| 수업 | 프로젝트에서 사용한 부분 |
| --- | --- |
| 2주차 웹과 REST API | FastAPI로 만든 REST API, 입력 검증과 오류 응답(422) |
| 3주차 결정적 처리와 확률적 생성 | 돈 계산은 같은 입력에 항상 같은 결과가 나와야 하므로 AI가 아닌 규칙 기반 엔진으로 계산 (N04) |
| 4주차 Docker와 Compose | 앱과 PostgreSQL을 Compose로 함께 실행, 볼륨으로 재실행 후 데이터 유지, 일반 계정 실행과 `.dockerignore` |
| 9·10주차 개발 방식 | 구현 결과를 보고 앞선 결정을 고치는 반복 개발 (8.3 변경 기록) |

## 2. 사용자 시나리오

모든 시나리오는 아래 **기준 예시 데이터**를 사용한다. (기준 월: 2026년 11월)

| 항목 | 값 |
| --- | --- |
| 월 수입 | 900,000원 |
| 고정 지출 | 200,000원 (통신비·교통비) |
| 최소 생활비 | 300,000원 |
| 목표 A: 비상금 저축 (우선순위 1) | 목표 1,200,000원, 현재 0원, 목표 월 2027년 4월 → 월 필요 200,000원 |
| 목표 B: 여행 (우선순위 2) | 목표 900,000원, 현재 300,000원, 목표 월 2027년 1월 → 월 필요 200,000원 |

### 시나리오 1. 월 수입 배분 (핵심)

- 상황: 사용자가 11월 아르바이트 급여 900,000원을 받았다.
- 행동: 수입을 등록하고 자동 배분을 실행한다.
- 처리: 고정 지출 → 최소 생활비 → 목표(우선순위 순) 순서로 배분한다.
- 결과: 고정 200,000 / 생활비 300,000 / 비상금 200,000 / 여행 200,000, 미배분 0원, 상태 "정상".

### 시나리오 2. 수입 감소 (핵심)

- 상황: 11월 실제 수입이 700,000원뿐이다.
- 행동: 수입을 수정하고 재배분을 실행한다.
- 처리: 고정 지출과 생활비를 먼저 확보한 뒤 남은 200,000원을 우선순위 1인 비상금에 배분한다. 여행 목표는 0원이 배분된다.
- 결과: 상태 "부분 배분", 여행 부족액 200,000원, 여행의 다음 달 필요 적립액이 200,000원에서 300,000원으로 증가했음을 표시한다.

### 시나리오 3. 추가 수입 발생

- 상황: 시나리오 2 이후 용돈 200,000원이 추가로 들어왔다.
- 행동: 추가 수입을 등록하고 "재배분"을 선택한다.
- 처리: 총수입 900,000원으로 엔진을 다시 실행한다.
- 결과: 여행에 200,000원이 배분되어 상태가 "정상"으로 바뀐다. "기존 유지"를 선택했다면 200,000원은 미배분 금액으로 남는다.

### 시나리오 4. 소비 기록과 잔액 확인

- 상황: 사용자가 생활비를 쓰고 있다.
- 행동: 생활비 소비 200,000원을 등록한다.
- 처리: 생활비 배분액에서 소비 합계를 뺀다.
- 결과: 생활비 잔액 100,000원. 이후 150,000원을 더 쓰면 잔액 -50,000원, "초과 소비"로 표시한다.

## 3. 요구사항 정의

### 3.1 기능 요구사항

| ID | 구분 | 기능명 | 요구사항 |
| --- | --- | --- | --- |
| R01 | 입력 | 수입 관리 | 수입 금액, 유형(급여·용돈·기타), 날짜, 메모를 등록·조회·수정·삭제할 수 있다. |
| R02 | 입력 | 목표 관리 | 목표명, 목표 금액, 현재 확보액, 목표 월, 우선순위를 등록·수정·삭제할 수 있다. 현재 확보액은 사용자가 실제로 모아 둔 금액이며 직접 갱신한다. |
| R03 | 입력 | 고정 지출 설정 | 월별 고정 지출 항목과 금액을 등록·수정·삭제할 수 있다. |
| R04 | 입력 | 최소 생활비 설정 | 월별 최소 생활비를 설정할 수 있다. |
| R05 | **엔진** | 월 필요 적립액 계산 | 목표 부족액과 남은 개월 수로 목표별 월 필요 적립액을 계산한다. |
| R06 | **엔진** | 자동 배분 | 고정 지출 → 최소 생활비 → 목표(우선순위 순) 순서로 배분안을 생성한다. |
| R07 | **엔진** | 배분 상태 판정 | 배분 결과를 정상·부분 배분·배분 불가로 판정하고 부족액과 다음 달 필요 적립액을 계산한다. |
| R08 | **엔진** | 재배분 | 수입·고정 지출·목표가 바뀌면 기존 배분 유지 또는 재배분을 선택해 다시 계산한다. |
| R09 | 엔진 | 배분 수동 수정 | 사용자가 목표 배분 금액을 직접 고칠 수 있다. 수정 후 배분 상태를 다시 판정한다. |
| R10 | 보조 | 소비 관리 | 소비 금액, 목적, 날짜, 메모를 등록·조회·수정·삭제할 수 있다. |
| R11 | 보조 | 목적별 잔액 | 목적별 배분액 − 소비 합계로 잔액을 계산하고, 음수이면 초과 소비로 표시한다. |
| R12 | 출력 | 월별 대시보드 | 선택한 월의 수입, 배분, 소비, 잔액, 배분 상태, 목표 달성률을 한 화면에 표시한다. |

엔진(R05~R09)이 서비스의 핵심이며, 다른 요구사항은 엔진에 값을 넣거나(입력) 결과를 보여주거나(출력) 실제 사용을 확인하는(보조) 역할이다.

### 3.2 비기능 요구사항

- N01: 금액은 원 단위 정수로 관리한다. 나누어떨어지지 않는 적립액은 올림한다.
- N02: 수입·소비·목표 금액은 0보다 큰 값만 등록할 수 있다.
- N03: 데이터는 PostgreSQL에 저장되어 프로그램을 다시 실행해도 유지된다.
- N04: 같은 입력에는 항상 같은 배분 결과를 반환한다. (우선순위가 같으면 목표 월이 빠른 순, 그다음 등록 순)
- N05: 잘못된 입력에는 원인을 알 수 있는 오류 메시지를 반환한다.
- N06: 재배분으로 배분액이 이미 쓴 금액보다 작아져도 소비 기록은 지우지 않고, 해당 목적을 초과 소비로 표시한다.
- N07: R01~R12의 기능을 브라우저 화면에서 사용할 수 있다. 화면은 API만 호출하고 계산은 하지 않는다.

### 3.3 핵심 요구사항 상세

#### R06·R07. 자동 배분과 상태 판정

| 항목 | 내용 |
| --- | --- |
| 입력 | 기준 월 (예: 2026-11) |
| 정상 처리 | 해당 월의 수입·고정 지출·최소 생활비·목표로 배분안을 계산해 저장하고, 상태(정상·부분 배분·배분 불가)를 판정 |
| 거절 조건 | 월 형식이 YYYY-MM이 아님 / 해당 월 최소 생활비가 설정되지 않음 |
| 거절 시 대응 | 422 형식 오류 / 404 "최소 생활비를 먼저 설정하세요". 기존 계획은 그대로 유지 |
| 처리 후 조회 | `GET /plans/{month}`, 대시보드에서 같은 배분안과 상태 확인 |

#### R08. 재배분 (기존 유지·재배분)

| 항목 | 내용 |
| --- | --- |
| 입력 | 기준 월, 방식(`reallocate` 또는 `keep`) |
| 정상 처리 | `reallocate`: 엔진을 다시 실행해 배분안을 새로 저장. `keep`: 기존 배분은 그대로 두고 수입 증가분을 미배분 금액에 더함 |
| 거절 조건 | `keep`인데 기존 계획이 없음 / 새 총수입 < 기존 총배분액 / 기존 계획이 배분 불가 상태 |
| 거절 시 대응 | 404 또는 409와 "재배분을 실행하세요" 안내. 기존 계획은 그대로 유지 |
| 처리 후 조회 | 응답에 이전 계획(previous)과 새 계획(current)을 함께 표시 |

#### R09. 배분 수동 수정

| 항목 | 내용 |
| --- | --- |
| 입력 | 기준 월, 수정할 배분 항목 id와 금액 목록 |
| 정상 처리 | 금액을 저장하고 목표별 상태, 다음 달 필요 적립액, 계획 상태, 미배분 금액을 다시 계산. 수정으로 줄어든 금액은 생활비에 더함 (C30) |
| 거절 조건 | 총배분액 > 총수입 / 고정 지출·생활비를 필요 금액보다 적게 수정 / 배분 불가 상태의 계획 / 계획에 없는 항목 id |
| 거절 시 대응 | 400(초과 금액 또는 사유 표시), 404. 저장된 금액은 바뀌지 않음 |
| 처리 후 조회 | `GET /plans/{month}`에 수정 금액과 다시 판정한 상태 표시 |

#### R02. 목표 삭제

| 항목 | 내용 |
| --- | --- |
| 입력 | 목표 id |
| 정상 처리 | 목표와 그 목표의 배분 항목을 삭제하고, 영향을 받은 배분 계획의 상태와 금액을 다시 계산 |
| 거절 조건 | 없는 목표 id / 그 목표로 등록된 소비 기록이 있음 |
| 거절 시 대응 | 404 / 409 "소비 기록을 먼저 삭제하세요". 목표와 계획은 그대로 유지 |
| 처리 후 조회 | 목표 목록과 배분 계획에서 해당 목표가 사라지고 계획 상태가 갱신됨 |

#### R10. 소비 등록

| 항목 | 내용 |
| --- | --- |
| 입력 | 금액, 목적(fixed·living·goal), 목표 id(목적이 goal일 때), 날짜, 메모 |
| 정상 처리 | 소비를 저장하고 해당 목적의 잔액과 초과 여부를 함께 반환 |
| 거절 조건 | 금액 ≤ 0 / 목적이 goal인데 목표 id가 없음 / 없는 목표 id |
| 거절 시 대응 | 422 / 404. 소비 기록은 추가되지 않음 |
| 처리 후 조회 | 소비 목록과 대시보드의 목적별 잔액에 반영 |

## 4. 구현 범위 및 우선순위

### 4.1 구현 범위

| 우선순위 | 기능 | 관련 요구사항 | 판단 근거 |
| --- | --- | --- | --- |
| P1 (핵심) | 배분 엔진: 적립액 계산, 자동 배분, 상태 판정, 재배분 | R05~R08 | 서비스의 존재 이유. 시나리오 1~3을 직접 수행 |
| P1 | 엔진 입력: 수입·목표·고정 지출·최소 생활비 | R01~R04 | 엔진이 계산하려면 반드시 필요 |
| P2 | 배분 수동 수정 | R09 | 자동 배분 결과가 사용자 사정과 다를 때 조정. 엔진 없이는 의미 없으므로 P1 이후 |
| P2 | 소비 기록과 목적별 잔액 | R10, R11 | 배분한 돈이 실제로 남았는지 확인하는 보조 기능 (시나리오 4) |
| P2 | 월별 대시보드 | R12 | 엔진 결과를 한 화면에 모아 보여주는 출력 |
| P2 | 브라우저 화면 | N07 | 직접 사용과 시연에 필요. API가 완성된 뒤 연결 |

P1을 먼저 완성하고 테스트로 검증한 뒤 P2를 구현한다. P1만으로도 "수입 → 배분 계획" 흐름이 동작해야 한다.

### 4.2 제외 범위

| 기능 | 제외 이유 |
| --- | --- |
| 은행 계좌·카드 결제 내역 자동 연동 | 금융기관 인증과 개인정보 처리가 필요해 과제 기간에 구현할 수 없음 |
| 영수증 OCR | 핵심 문제(수입 배분)와 직접 관련이 없음 |
| 금융 상품 가입 및 송금 | 실제 금융 거래는 서비스 범위 밖 |
| 전월 대비 분석 그래프 | 한 달 안의 배분 문제를 먼저 해결하는 데 집중 (C05) |
| AI 기반 배분 설명·소비 예측 | 배분 계산은 결과가 항상 같아야 하므로 엔진이 담당. 설명 기능은 확장 계획으로 둠 (C05, 10장) |
| 배분 계획 확정과 월 사이 확보액 누적 | 시나리오가 한 달 안에서 끝나고, 확정 후 수정·이중 계산 문제를 만듦 (C16) |

## 5. 배분 엔진 설계

### 5.1 입력

| 입력값 | 설명 |
| --- | --- |
| 기준 월 M | 배분할 월 (예: 2026-11) |
| 총수입 I | 해당 월에 등록된 수입 합계 |
| 고정 지출 F | 해당 월 고정 지출 합계 |
| 최소 생활비 L | 해당 월 최소 생활비 |
| 목표 목록 | 목표별 목표 금액 T, 확보액 C, 목표 월 D, 우선순위 P |

확보액 C = 사용자가 입력한 현재 확보액. 사용자가 실제로 돈을 모으면 목표의 현재 확보액을 직접 수정한다. (C16)

### 5.2 계산식

남은 개월 수 (기준 월 포함):

```
n = (D의 연도 × 12 + D의 월) − (M의 연도 × 12 + M의 월) + 1
```

예: 기준 월 2026-11, 목표 월 2027-01 → n = 3 (11월, 12월, 1월)

목표 부족액:

```
S = T − C
```

월 필요 적립액:

```
R = ⌈ S ÷ n ⌉   (원 단위 올림)
```

배분 가능 금액:

```
A = I − F − L
```

다음 달 필요 적립액 (이번 달 배분액 a가 R보다 작을 때):

```
R' = ⌈ (S − a) ÷ (n − 1) ⌉
```

목적별 잔액 = 목적별 배분액 − 목적별 소비 합계

목표 달성률 = C ÷ T × 100 (소수 첫째 자리까지)

### 5.3 배분 순서

1. 총수입 I를 계산한다.
2. 고정 지출 F를 확보한다. I < F이면 **배분 불가**, 부족액 = F − I.
3. 최소 생활비 L을 확보한다. I − F < L이면 **배분 불가**, 부족액 = L − (I − F).
4. 남은 금액 A를 우선순위 순으로 목표에 배분한다. 각 목표에는 min(R, 남은 금액)을 배분한다.
5. 필요 적립액을 다 받지 못한 목표가 있으면 **부분 배분**. 해당 목표의 부족액(R − a)과 다음 달 필요 적립액 R'을 표시한다.
6. 모든 목표를 채우고 남은 금액은 **미배분 금액**으로 둔다. 사용자는 이를 원하는 목표에 수동 배분할 수 있다(R09).
7. 총배분액 + 미배분 금액 = 총수입인지 확인한다.

배분 불가일 때도 목표별 필요 적립액과 다음 달 필요 적립액은 계산해 표시한다. 이번 달에 넣지 못하면 다음 달에 얼마가 필요한지 알려주기 위해서다.

### 5.4 배분 상태

| 상태 | 조건 | 표시 내용 |
| --- | --- | --- |
| 정상 | 모든 목표가 필요 적립액을 받음 | 미배분 금액 |
| 부분 배분 | 생활비까지는 확보했지만 일부 목표가 부족 | 부족한 목표, 부족액, 다음 달 필요 적립액 |
| 배분 불가 | 고정 지출 또는 최소 생활비를 확보하지 못함 | 부족액, 조정 대상(고정 지출·생활비) |

### 5.5 재배분 방식

| 변화 | 선택지 | 처리 |
| --- | --- | --- |
| 수입 증가 | 기존 유지 | 기존 배분 그대로, 증가분은 미배분 금액에 더함 |
| 수입 증가 | 재배분 | 새 총수입으로 엔진을 다시 실행 |
| 수입 감소 (새 총수입 < 기존 총배분액) | 재배분만 가능 | 기존 배분이 수입을 넘으므로 유지할 수 없음 (C10) |
| 기존 계획이 배분 불가 | 재배분만 가능 | 상태와 부족액이 갱신되지 않아 결과가 모순되므로 유지할 수 없음 (C17) |
| 고정 지출·목표 변경 | 재배분 | 엔진을 다시 실행 |

재배분하면 수동 수정한 금액은 초기화된다. 재배분 결과는 바로 저장되고, 응답에 이전 계획을 함께 담아 화면에서 나란히 보여준다. (C09)

### 5.6 수동 수정 후 재판정

수동 수정(R09)은 주로 목표 배분 금액을 바꾸는 기능이다. 고정 지출과 최소 생활비는 필수 확보 항목이므로 필요 금액보다 줄일 수 없고, 늘리는 것만 API로 허용한다. 화면에서는 목표 배분 금액만 입력칸으로 수정한다. (C18, C22)

수정이 저장되면 엔진의 재판정 함수가 수정된 금액으로 상태를 다시 계산한다.

1. 목표마다 n, S, R을 다시 계산한다.
2. 배분액 a ≥ R이면 "충족", a < R이면 "부족"(n = 1이면 "목표 미달 예정")으로 판정하고 R'을 계산한다.
3. 부족한 목표가 있으면 계획 상태는 "부분 배분", 없으면 "정상"이다.
4. 수정으로 총배분액이 줄었으면 줄어든 금액을 생활비에 더한다. 수정 전부터 있던 미배분 금액(예: "기존 유지"로 남은 증가분)은 그대로 둔다. (C30)
5. 미배분 금액 = 총수입 − 총배분액.

예: AT03 상태에서 여행을 0원으로 수정하면 줄어든 200,000원이 생활비로 가서 생활비 500,000원, 미배분 0원, 여행 "부족"(다음 달 300,000원), 계획 "부분 배분"이다.

예: 시나리오 2(수입 700,000원)에서 비상금 100,000원, 여행 100,000원으로 나누면 두 목표 모두 "부족", 다음 달 필요 적립액은 비상금 220,000원, 여행 250,000원, 계획 상태는 "부분 배분"이다.

목표를 삭제할 때도 같은 함수로 남은 금액의 상태를 다시 판정한다.

### 5.7 예외 처리

| 상황 | 처리 |
| --- | --- |
| 부족액 S ≤ 0 | "목표 달성" 상태, 배분에서 제외 |
| 목표 월이 기준 월보다 이전 (n < 1) | "목표 기간 오류", 배분에서 제외하고 목표 수정 안내 |
| 목표 월이 기준 월과 같음 (n = 1) | 부족액 전체가 이번 달 필요 적립액. 다 못 받으면 "목표 미달 예정" 표시 |
| 수동 수정으로 총배분액 > 총수입 | 저장 거부, 초과 금액 표시 |
| 수동 수정으로 고정 지출·생활비 < 필요 금액 | 저장 거부, 필요 금액 안내 |
| 배분 불가 계획을 수동 수정 | 저장 거부, 수입이나 설정을 조정한 뒤 재배분 안내 |
| 배분 불가 계획에서 "기존 유지" | 거부, 재배분 안내 |
| 소비 기록이 있는 목표 삭제 | 거부(409), 소비를 먼저 삭제하도록 안내 |
| 소비 합계 > 배분액 | 잔액을 음수로 표시하고 "초과 소비" 표시 |
| 금액 ≤ 0 또는 정수가 아님 | 입력 오류 (422) 반환 |

## 6. 프로그램 설계

### 6.1 구성 요소와 책임

| 구성 요소 | 책임 | 의존 관계 |
| --- | --- | --- |
| 화면 (`frontend/`) | 입력 폼과 결과 표시. 계산은 하지 않고 API를 호출해 결과만 보여줌 | 요청 처리 |
| 요청 처리 (`app/routers/`) | 요청을 받아 입력을 확인하고, 기능 처리를 호출한 뒤 응답을 돌려줌 | 기능 처리, 데이터 접근 |
| 기능 처리 (`app/services/`) | 배분·소비·대시보드처럼 계산이 필요한 일. DB에서 필요한 값을 모아 엔진에 넘기고 결과를 저장 | 배분 엔진, 데이터 접근 |
| 배분 엔진 (`app/engine.py`) | 5장의 계산만 담당. DB를 쓰지 않음 | 없음 |
| 입력 형식 (`app/schemas.py`) | 요청·응답의 형식과 입력 검사 규칙 (Pydantic) | 없음 |
| 데이터 접근 (`app/models.py`, `app/database.py`) | 테이블 정의, DB 읽기·쓰기 | PostgreSQL |

배분 엔진이 하는 일은 세 가지다.

| 엔진 기능 | 하는 일 | 쓰는 곳 |
| --- | --- | --- |
| 자동 배분 (`allocate`) | 5.3 순서로 배분하고 상태 판정 | 자동 배분, 재배분 |
| 기존 유지 (`keep_existing`) | 기존 배분은 그대로 두고, 늘어난 수입을 미배분 금액에 더함 (5.5) | 기존 유지 |
| 다시 판정 (`evaluate`) | 사용자가 정한 금액으로 상태만 다시 판정 (5.6) | 수동 수정, 목표 삭제 |

이 밖에 남은 개월 수 n과 월 필요 적립액 R을 구하는 작은 계산 함수가 있다. 자동 배분과 다시 판정은 목표 상태를 정하는 같은 계산을 쓰므로, 금액이 같으면 판정 결과도 같다(테스트로 확인).

배분 엔진을 DB와 분리한 이유: DB 없이 엔진만 따로 시험할 수 있어 같은 입력에 같은 결과가 나오는지(N04) 바로 확인할 수 있고, 재배분도 같은 계산을 다시 실행하면 되기 때문이다.

계산이 없는 단순 저장·조회(수입·고정 지출·최소 생활비, 목표의 등록·조회·수정)는 요청 처리에서 바로 데이터 접근을 사용한다. 배분·소비·대시보드·목표 삭제는 계산이 필요하므로 기능 처리를 거친다. (C14, C19, C24)

### 6.2 실행 흐름

자동 배분 / 재배분:

```
화면 [자동 배분] 버튼
→ 요청 처리: POST /plans/{month}/allocate, 월 형식 확인
→ 기능 처리: 그 달의 수입·고정 지출·최소 생활비·목표를 DB에서 읽음
→ 배분 엔진: 배분안과 상태 계산
→ 기능 처리: 배분 계획을 DB에 저장
→ 화면: 상태, 배분 표, 이전 배분과 비교, 부족 안내 표시
```

수동 수정:

```
화면 [수정 저장] 버튼
→ 요청 처리: PUT /plans/{month}/allocations
→ 기능 처리: 거절 조건 확인 (배분 불가 계획, 계획에 없는 항목, 총수입 초과, 고정 지출·생활비를 필요 금액보다 적게)
             거절이면 400 또는 404로 응답하고 저장하지 않음
→ 배분 엔진: 수정한 금액으로 상태 다시 판정. 줄어든 금액은 생활비에 더함 (C30)
→ 기능 처리: 금액과 상태를 DB에 저장
→ 화면: 갱신된 계획 표시
```

목표 삭제:

```
화면 목표 [삭제] 버튼
→ 요청 처리: DELETE /goals/{id}
→ 기능 처리: 이 목표로 등록된 소비가 있으면 409(현재 상태와 충돌)로 거절
→ 기능 처리: 목표와 그 목표의 배분 항목 삭제
→ 배분 엔진: 남은 배분 계획의 상태 다시 판정
→ 응답: 204 (성공, 돌려줄 내용 없음)
```

소비 등록:

```
화면 소비 등록 폼
→ 요청 처리: POST /expenses, 금액·목적 확인
→ 기능 처리: 소비 저장, 그 목적의 잔액 계산
→ 화면: 잔액과 초과 소비 여부 표시
```

| MonthlySetting (월 설정) | 월, 최소 생활비 |
| AllocationPlan (배분 계획) | 월별 배분 계획 한 개: 총수입, 총배분액, 미배분 금액, 상태, 배분 불가일 때의 부족액과 부족한 항목(고정 지출·생활비) |
| Allocation (배분 항목) | 계획 안의 한 줄(고정 지출·생활비·목표 중 하나): 필요 금액, 배분 금액, 목표별 상태(충족·부족·목표 미달 예정·목표 달성·기간 오류), 다음 달 필요 적립액 R', 수동 수정 여부 |
| Expense (소비) | 금액, 목적(고정 지출·생활비·목표), 목표(목적이 목표일 때), 날짜, 메모 |

관계: 배분 계획 하나에 배분 항목 여러 개가 속한다. 목표 하나에는 배분 항목과 소비 기록이 여러 개 연결될 수 있다.

계획을 조회할 때 목표별 남은 개월 수 n과 부족액 S는 저장하지 않고 목표 정보로 다시 계산한다. (C08, C12)

### 6.5 실행·배포 구조

```
[브라우저]
   │  http://localhost:8000      (화면 /, API 문서 /docs)
   ▼
[api 컨테이너]  FastAPI + 화면 파일(frontend/), 일반 계정 appuser로 실행
   │  postgresql+psycopg://...@db:5432   (Compose 내부 네트워크의 서비스 이름 db)
   ▼
[db 컨테이너]   PostgreSQL 16
   │
   ▼
[pgdata 볼륨]   DB 데이터 보관. 컨테이너를 지워도 유지
```

| 구성 요소 | 실행 위치 | 접속 주소 | 설정 |
| --- | --- | --- | --- |
| 화면 | 사용자 브라우저 (파일은 api 컨테이너가 제공) | `http://localhost:8000` | 없음 |
| API 서버 | api 컨테이너 | 호스트 8000 → 컨테이너 8000 | `.env`의 `DATABASE_URL` |
| DB | db 컨테이너 | Compose 내부 `db:5432` (외부에 공개하지 않음) | `.env`의 `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` |
| 테스트 DB | 같은 db 컨테이너의 `moneyplan_test` | `db:5432` | `.env`의 `TEST_DATABASE_URL`, `db/init/01_create_test_db.sql` |
| 데이터 | `pgdata` 볼륨 | – | `docker-compose.yml`의 `volumes` |

`.env`는 `.dockerignore`로 이미지에서 제외하고, 실행할 때 Compose가 환경변수로 전달한다. 코드를 바꾸면 이미지를 다시 빌드해 같은 이미지로 실행한다. (C20)

이미지에는 `app/`, `frontend/`, `tests/`, `seed.py`, `requirements.txt`만 들어간다. `/code`는 root 소유이고 앱은 appuser로 실행되므로, pytest 캐시는 `PYTEST_ADDOPTS="-p no:cacheprovider"`로 끈다. (C26)

## 9. 실행 및 사용 안내

### 9.1 실행 환경

- Docker Desktop (Docker Compose 포함)
- (컨테이너 내부) Python 3.12, FastAPI, PostgreSQL 16
- 브라우저 (Chrome, Edge 등)

### 9.2 실행 절차

1. 소스 코드를 준비하고 `moneyplan` 폴더로 이동한다. 저장소는 비공개이므로 아래 둘 중 하나를 쓴다.

    - 제출한 압축 파일: 압축을 풀고 그 안의 `moneyplan` 폴더로 이동한다.
    - 저장소 접근 권한을 받은 경우: 저장소를 내려받은 뒤 이동한다.

    ```bash
    git clone <저장소 주소>
    cd cloud_programming_project/moneyplan
    ```

2. 환경변수 파일을 만든다.

    ```bash
    cp .env.example .env
    ```

    Windows PowerShell에서는 `copy .env.example .env`를 쓴다.

    `.env` 예시:

    ```
    POSTGRES_USER=moneyplan
    POSTGRES_PASSWORD=moneyplan
    POSTGRES_DB=moneyplan
    DATABASE_URL=postgresql+psycopg://moneyplan:moneyplan@db:5432/moneyplan
    TEST_DATABASE_URL=postgresql+psycopg://moneyplan:moneyplan@db:5432/moneyplan_test
    ```

3. 데이터베이스와 API 서버를 실행한다.

    ```bash
    docker compose up -d --build
    ```

4. 브라우저에서 `http://localhost:8000`에 접속한다. API 문서는 `http://localhost:8000/docs`에 있다.
5. (선택) 기준 예시 데이터를 넣는다.

    ```bash
    docker compose exec api python seed.py
    ```

6. 테스트를 실행한다.

    ```bash
    docker compose exec api pytest
    ```

7. 종료: `docker compose down` (데이터는 볼륨에 유지됨. 데이터까지 지우려면 `docker compose down -v`)

코드를 수정한 뒤에는 `docker compose up -d --build`로 이미지를 다시 빌드해야 반영된다. 테이블 구조가 바뀐 경우(C16 이후 처음 실행할 때 등)에는 `docker compose down -v`로 DB를 비운 뒤 다시 실행한다.

### 9.3 사용 방법

화면 상단에서 월을 고른 뒤 탭을 차례로 사용한다.

1. **입력** 탭: 수입, 고정 지출, 최소 생활비, 목표를 등록한다.
2. **배분** 탭: [자동 배분]을 누르면 상태(정상·부분 배분·배분 불가)와 배분 표가 나온다.
3. 필요하면 배분 표에서 목표 금액을 고치고 [수정 저장]을 누른다. 상태가 다시 판정된다. 저장이 거부되면 사유가 빨간 글씨로 표시된다.
   - [자동 배분]·[기존 유지] 직후에는 "이전 배분" 열이 회색으로 함께 표시된다. 다른 탭이나 월로 이동했다 오면 사라진다. (C25)
4. 수입이 바뀌면 입력 탭에서 수입을 수정·추가한 뒤, 배분 탭에서 [자동 배분](재배분) 또는 [기존 유지]를 누른다. 대시보드에 "재배분이 필요합니다"가 보이면 재배분을 실행한다.
5. **소비** 탭: 소비를 등록하면 그 목적의 잔액이 바로 표시된다.
6. **대시보드** 탭: 목적별 잔액, 초과 소비, 목표 달성률을 확인한다.

같은 기능을 API로 사용하려면 `/docs`에서 6.3의 경로를 호출한다.

### 9.4 수동 확인 절차

AT11 (재실행 후 데이터 유지):

1. 시드 데이터를 넣고 자동 배분, 소비 1건 등록
2. `docker compose down` 후 `docker compose up -d`
3. 대시보드에서 수입·배분·소비가 그대로인지 확인

AT12 (화면 시나리오):

1. `docker compose down -v` → `docker compose up -d --build` → `docker compose exec api python seed.py`
2. 배분 탭 [자동 배분] → 정상, 미배분 0원 (시나리오 1)
3. 입력 탭에서 급여를 700,000원으로 수정 → 배분 탭 [자동 배분] → 부분 배분, 여행 다음 달 300,000원 (시나리오 2)
4. 용돈 200,000원 추가 → [자동 배분] → 정상 (시나리오 3)
5. 소비 탭에서 생활비 200,000원, 150,000원 등록 → 잔액 100,000원, −50,000원 초과 소비 (시나리오 4)

| 5 | AI 배분 결과 설명 | 배분 결과를 한두 문장으로 설명 (예: "수입이 줄어 여행 적립이 0원이 되었고, 다음 달에는 30만 원이 필요해요") | 상태 배지와 숫자만으로는 이유를 바로 이해하기 어려울 수 있음 (8.3 추가 점검 질문) | 계산은 엔진이 그대로 하고 설명만 외부 AI에 요청 (N04, C05). AI 호출이 실패해도 배분 결과는 그대로 표시 |
| 6 | 월별 비교와 생활비 추천 | 월별 수입·배분·소비 변화 그래프, 지난 소비로 적정 최소 생활비 제안 | 여러 달을 쓰기 시작하면 필요 (C05에서 제외) | 1번(월 마감)으로 여러 달 데이터가 이어진 뒤에 의미가 있음 |
