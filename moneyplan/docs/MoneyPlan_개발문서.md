# MoneyPlan

## 목표 기반 월별 자금 배분 서비스 개발 문서

> **핵심 한 문장**
> 수입이 들어오거나 바뀌었을 때, 목표를 지키려면 이번 달 어디에 얼마를 넣어야 하는지 계산해 준다.

---

## 1. 프로젝트 개요

### 1.1 프로젝트명

MoneyPlan – 목표 기반 월별 자금 배분 서비스

### 1.2 프로젝트 목적

MoneyPlan은 사용자가 월 수입을 받았을 때 고정 지출, 최소 생활비, 미래 목표(저축·여행 등)를 고려하여 **이번 달 배분 계획을 자동으로 계산**하는 서비스이다.

기존 가계부가 "쓴 돈을 기록"하는 데 초점을 둔다면, MoneyPlan은 "들어온 돈을 어떻게 나눌지"를 먼저 계산한다. 수입이 늘거나 줄면 같은 계산을 다시 실행하여, 어떤 목표가 영향을 받는지 보여준다.

서비스의 중심은 **배분 엔진** 하나이며, 나머지 기능은 엔진의 입력(수입·목표·지출 설정), 출력(대시보드), 보조(소비 기록과 잔액 확인) 역할을 한다.

### 1.3 대상 사용자

- 아르바이트나 급여로 매월 수입이 있는 대학생
- 생활비를 쓰면서 동시에 저축·여행 같은 목표 자금을 모으는 사용자
- 달마다 수입이 달라 배분 계획을 자주 조정해야 하는 사용자

### 1.4 해결하려는 문제

| 번호 | 문제 | MoneyPlan의 해결 방식 |
| --- | --- | --- |
| 1 | 수입을 각 목적에 얼마씩 나눌지 판단하기 어렵다 | 정해진 순서와 우선순위로 자동 배분 |
| 2 | 목표 달성을 위해 매월 얼마를 모아야 하는지 계산하기 어렵다 | 부족액 ÷ 남은 개월 수로 월 필요 적립액 계산 |
| 3 | 수입이 줄었을 때 무엇을 줄여야 하는지 모른다 | 우선순위가 낮은 목표부터 감액하고, 다음 달 필요 적립액을 다시 계산 |
| 4 | 추가 수입이 생겼을 때 기존 계획을 어떻게 바꿔야 할지 모른다 | 기존 배분 유지 또는 재배분 중 선택 |
| 5 | 배분한 돈이 실제로 얼마 남았는지 알기 어렵다 | 목적별 소비를 기록하고 잔액·초과 여부 표시 |

## 2. 사용자 시나리오

모든 시나리오는 아래 **기준 예시 데이터**를 사용한다. (기준 월: 2026년 11월)

| 항목 | 값 |
| --- | --- |
| 월 수입 | 900,000원 |
| 고정 지출 | 200,000원 (통신비·교통비) |
| 최소 생활비 | 300,000원 |
| 목표 A: 비상금 저축 (우선순위 1) | 목표 1,200,000원, 현재 0원, 목표 월 2027년 4월 → 월 필요 200,000원 |
| 목표 B: 여행 (우선순위 2) | 목표 900,000원, 현재 300,000원, 목표 월 2027년 1월 → 월 필요 200,000원 |

### 시나리오 1. 월 수입 배분 (핵심)

- 상황: 사용자가 11월 아르바이트 급여 900,000원을 받았다.
- 행동: 수입을 등록하고 자동 배분을 실행한다.
- 처리: 고정 지출 → 최소 생활비 → 목표(우선순위 순) 순서로 배분한다.
- 결과: 고정 200,000 / 생활비 300,000 / 비상금 200,000 / 여행 200,000, 미배분 0원, 상태 "정상".

### 시나리오 2. 수입 감소 (핵심)

- 상황: 11월 실제 수입이 700,000원뿐이다.
- 행동: 수입을 수정하고 재배분을 실행한다.
- 처리: 고정 지출과 생활비를 먼저 확보한 뒤 남은 200,000원을 우선순위 1인 비상금에 배분한다. 여행 목표는 0원이 배분된다.
- 결과: 상태 "부분 배분", 여행 부족액 200,000원, 여행의 다음 달 필요 적립액이 200,000원에서 300,000원으로 증가했음을 표시한다.

### 시나리오 3. 추가 수입 발생

- 상황: 시나리오 2 이후 용돈 200,000원이 추가로 들어왔다.
- 행동: 추가 수입을 등록하고 "재배분"을 선택한다.
- 처리: 총수입 900,000원으로 엔진을 다시 실행한다.
- 결과: 여행에 200,000원이 배분되어 상태가 "정상"으로 바뀐다. "기존 유지"를 선택했다면 200,000원은 미배분 금액으로 남는다.

### 시나리오 4. 소비 기록과 잔액 확인

- 상황: 사용자가 생활비를 쓰고 있다.
- 행동: 생활비 소비 200,000원을 등록한다.
- 처리: 생활비 배분액에서 소비 합계를 뺀다.
- 결과: 생활비 잔액 100,000원. 이후 150,000원을 더 쓰면 잔액 -50,000원, "초과 소비"로 표시한다.

## 3. 요구사항 정의

### 3.1 기능 요구사항

| ID | 구분 | 기능명 | 요구사항 |
| --- | --- | --- | --- |
| R01 | 입력 | 수입 관리 | 수입 금액, 유형(급여·용돈·기타), 날짜, 메모를 등록·조회·수정·삭제할 수 있다. |
| R02 | 입력 | 목표 관리 | 목표명, 목표 금액, 현재 확보액, 목표 월, 우선순위를 등록·수정·삭제할 수 있다. |
| R03 | 입력 | 고정 지출 설정 | 월별 고정 지출 항목과 금액을 등록·삭제할 수 있다. |
| R04 | 입력 | 최소 생활비 설정 | 월별 최소 생활비를 설정할 수 있다. |
| R05 | **엔진** | 월 필요 적립액 계산 | 목표 부족액과 남은 개월 수로 목표별 월 필요 적립액을 계산한다. |
| R06 | **엔진** | 자동 배분 | 고정 지출 → 최소 생활비 → 목표(우선순위 순) 순서로 배분안을 생성한다. |
| R07 | **엔진** | 배분 상태 판정 | 배분 결과를 정상·부분 배분·배분 불가로 판정하고 부족액과 다음 달 필요 적립액을 계산한다. |
| R08 | **엔진** | 재배분 | 수입·고정 지출·목표가 바뀌면 기존 배분 유지 또는 재배분을 선택해 다시 계산한다. |
| R09 | 엔진 | 배분 수동 수정 | 사용자가 배분 금액을 직접 고칠 수 있으며, 총배분액이 총수입을 넘으면 저장을 거부한다. |
| R10 | 보조 | 소비 관리 | 소비 금액, 목적, 날짜, 메모를 등록·조회·수정·삭제할 수 있다. |
| R11 | 보조 | 목적별 잔액 | 목적별 배분액 − 소비 합계로 잔액을 계산하고, 음수이면 초과 소비로 표시한다. |
| R12 | 출력 | 월별 대시보드 | 선택한 월의 수입, 배분, 소비, 잔액, 배분 상태, 목표 달성률을 한 화면에 표시한다. |

엔진(R05~R09)이 서비스의 핵심이며, 다른 요구사항은 엔진에 값을 넣거나(입력) 결과를 보여주거나(출력) 실제 사용을 확인하는(보조) 역할이다.

### 3.2 비기능 요구사항

- N01: 금액은 원 단위 정수로 관리한다. 나누어떨어지지 않는 적립액은 올림한다.
- N02: 수입·소비·목표 금액은 0보다 큰 값만 등록할 수 있다.
- N03: 데이터는 PostgreSQL에 저장되어 프로그램을 다시 실행해도 유지된다.
- N04: 같은 입력에는 항상 같은 배분 결과를 반환한다. (우선순위가 같으면 목표 월이 빠른 순, 그다음 등록 순)
- N05: 잘못된 입력에는 원인을 알 수 있는 오류 메시지를 반환한다.
- N06: 재배분으로 배분액이 이미 쓴 금액보다 작아져도 소비 기록은 지우지 않고, 해당 목적을 초과 소비로 표시한다.

## 5. 배분 엔진 설계

### 5.1 입력

| 입력값 | 설명 |
| --- | --- |
| 기준 월 M | 배분할 월 (예: 2026-11) |
| 총수입 I | 해당 월에 등록된 수입 합계 |
| 고정 지출 F | 해당 월 고정 지출 합계 |
| 최소 생활비 L | 해당 월 최소 생활비 |
| 목표 목록 | 목표별 목표 금액 T, 확보액 C, 목표 월 D, 우선순위 P |

확보액 C = 사용자가 입력한 현재 확보액 + 이전 달까지 확정된 배분 계획에서 해당 목표에 배분된 금액 합계

### 5.2 계산식

남은 개월 수 (기준 월 포함):

```
n = (D의 연도 × 12 + D의 월) − (M의 연도 × 12 + M의 월) + 1
```

예: 기준 월 2026-11, 목표 월 2027-01 → n = 3 (11월, 12월, 1월)

목표 부족액:

```
S = T − C
```

월 필요 적립액:

```
R = ⌈ S ÷ n ⌉   (원 단위 올림)
```

배분 가능 금액:

```
A = I − F − L
```

다음 달 필요 적립액 (이번 달 배분액 a가 R보다 작을 때):

```
R' = ⌈ (S − a) ÷ (n − 1) ⌉
```

목적별 잔액 = 목적별 배분액 − 목적별 소비 합계

목표 달성률 = C ÷ T × 100

### 5.3 배분 순서

1. 총수입 I를 계산한다.
2. 고정 지출 F를 확보한다. I < F이면 **배분 불가**, 부족액 = F − I.
3. 최소 생활비 L을 확보한다. I − F < L이면 **배분 불가**, 부족액 = L − (I − F).
4. 남은 금액 A를 우선순위 순으로 목표에 배분한다. 각 목표에는 min(R, 남은 금액)을 배분한다.
5. 필요 적립액을 다 받지 못한 목표가 있으면 **부분 배분**. 해당 목표의 부족액(R − a)과 다음 달 필요 적립액 R'을 표시한다.
6. 모든 목표를 채우고 남은 금액은 **미배분 금액**으로 둔다. 사용자는 이를 원하는 목적에 수동 배분할 수 있다(R09).
7. 총배분액 + 미배분 금액 = 총수입인지 확인한다.

### 5.4 배분 상태

| 상태 | 조건 | 표시 내용 |
| --- | --- | --- |
| 정상 | 모든 목표가 필요 적립액을 받음 | 미배분 금액 |
| 부분 배분 | 생활비까지는 확보했지만 일부 목표가 부족 | 부족한 목표, 부족액, 다음 달 필요 적립액 |
| 배분 불가 | 고정 지출 또는 최소 생활비를 확보하지 못함 | 부족액, 조정 대상(고정 지출·생활비) |

### 5.5 재배분 방식

| 변화 | 선택지 | 처리 |
| --- | --- | --- |
| 수입 증가 | 기존 유지 | 기존 배분 그대로, 증가분은 미배분 금액에 더함 |
| 수입 증가 | 재배분 | 새 총수입으로 엔진을 다시 실행 |
| 수입 감소 | 재배분만 가능 | 새 총수입으로 엔진을 다시 실행 (기존 배분은 수입을 초과하므로 유지 불가) |
| 고정 지출·목표 변경 | 재배분 | 엔진을 다시 실행 |

재배분하면 수동 수정한 금액은 초기화된다. 재배분 결과는 기존 계획과 나란히 보여주고, 사용자가 확인한 뒤 저장한다.

### 5.6 예외 처리

| 상황 | 처리 |
| --- | --- |
| 부족액 S ≤ 0 | "목표 달성" 상태, 배분에서 제외 |
| 목표 월이 기준 월보다 이전 (n < 1) | "목표 기간 오류", 배분에서 제외하고 목표 수정 안내 |
| 목표 월이 기준 월과 같음 (n = 1) | 부족액 전체가 이번 달 필요 적립액. 다 못 받으면 "목표 미달 예정" 표시 |
| 수동 수정으로 총배분액 > 총수입 | 저장 거부, 초과 금액 표시 |
| 소비 합계 > 배분액 | 잔액을 음수로 표시하고 "초과 소비" 표시 |
| 금액 ≤ 0 또는 정수가 아님 | 입력 오류 (422) 반환 |

## 6. 프로그램 설계

### 6.1 구성 요소와 책임

| 구성 요소 | 책임 | 의존 관계 |
| --- | --- | --- |
| 배분 엔진 (`engine.py`) | 5장의 계산을 수행하는 순수 함수. DB를 사용하지 않는다. | 없음 |
| API 라우터 (`routers/`) | 요청 수신, 입력 검증, 서비스 호출, 응답 반환 | 서비스 |
| 서비스 (`services/`) | DB에서 엔진 입력을 모으고, 엔진 결과를 저장 | 엔진, 저장소 |
| 저장소 (`models.py`, `database.py`) | 테이블 정의와 DB 접근 | PostgreSQL |
| 스키마 (`schemas.py`) | 요청·응답 형식과 입력 검증 규칙 (Pydantic) | 없음 |

배분 엔진을 DB와 분리한 이유: 같은 입력에 같은 결과를 내는지(N04) 단위 테스트로 바로 확인할 수 있고, 재배분도 같은 함수를 다시 호출하는 것으로 처리할 수 있기 때문이다.

### 6.2 실행 흐름

자동 배분 / 재배분:

```
사용자 요청 (POST /plans/{month}/allocate)
→ API 라우터: 월 형식 검증
→ 서비스: 해당 월의 수입·고정 지출·생활비·목표를 DB에서 조회
→ 배분 엔진: 배분안과 상태 계산
→ 서비스: AllocationPlan, Allocation 저장 (초안)
→ 응답: 배분안, 상태, 부족액, 다음 달 필요 적립액
```

소비 등록:

```
사용자 요청 (POST /expenses)
→ API 라우터: 금액·목적 검증
→ 서비스: Expense 저장
→ 서비스: 해당 목적의 소비 합계와 잔액 계산
→ 응답: 등록된 소비, 목적별 잔액, 초과 여부
```

- 다음 달 필요 적립액 표시가 계획 수정에 실제로 도움이 되는가?

## 9. 실행 및 사용 안내

### 9.1 실행 환경

- Docker, Docker Compose
- (컨테이너 내부) Python 3.12, FastAPI, PostgreSQL 16

### 9.2 실행 절차

1. 소스 코드를 내려받는다.

    ```bash
    git clone <저장소 주소>
    cd moneyplan
    ```

2. 환경변수 파일을 만든다.

    ```bash
    cp .env.example .env
    ```

    `.env` 예시:

    ```
    POSTGRES_USER=moneyplan
    POSTGRES_PASSWORD=moneyplan
    POSTGRES_DB=moneyplan
    DATABASE_URL=postgresql+psycopg://moneyplan:moneyplan@db:5432/moneyplan
    TEST_DATABASE_URL=postgresql+psycopg://moneyplan:moneyplan@db:5432/moneyplan_test
    ```

3. 데이터베이스와 API 서버를 실행한다.

    ```bash
    docker compose up -d --build
    ```

    Windows에서 `failed to execute bake` 오류가 나면 드라이브 문자를 대문자로 쓴 경로(`C:\...`)로 이동한 뒤 다시 실행한다. (8.2 참고)

4. 브라우저에서 API 문서에 접속한다: `http://localhost:8000/docs`
5. (선택) 기준 예시 데이터를 넣는다.

    ```bash
    docker compose exec api python seed.py
    ```

6. 테스트를 실행한다.

    ```bash
    docker compose exec api pytest
    ```

7. 종료: `docker compose down` (데이터는 볼륨에 유지됨. 데이터까지 지우려면 `docker compose down -v`)

### 9.3 사용 방법

1. `/incomes`에 이번 달 수입을 등록한다.
2. `/goals`에 목표를 등록한다. (목표 금액, 현재 확보액, 목표 월, 우선순위)
3. `/fixed-expenses`와 `/settings/{month}`로 고정 지출과 최소 생활비를 설정한다.
4. `/plans/{month}/allocate`로 자동 배분을 실행하고 상태를 확인한다.
5. 필요하면 `/plans/{month}/allocations`로 금액을 수정한 뒤 `/plans/{month}/confirm`으로 확정한다.
6. 수입이 바뀌면 수입을 수정·추가하고 `/plans/{month}/allocate?mode=keep` 또는 `mode=reallocate`로 다시 실행한다.
7. `/expenses`에 소비를 등록하고 `/dashboard/{month}`에서 잔액과 목표 달성률을 확인한다.
